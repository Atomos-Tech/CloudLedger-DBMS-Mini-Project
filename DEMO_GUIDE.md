# CloudLedger — Demo Guide

A presenter's guide: how to run the app, what's on each screen, and a
scripted walkthrough that hits every notable feature in about 5-7 minutes.
For setup/architecture details see [`README.md`](README.md).

## 1. Before you present — get it running

```bash
# 1. Start the databases (if using the included docker-compose)
docker compose up -d

# 2. Load schema + demo data (only needed once, or after a reset)
mysql -u root -p < db/mysql/schema.sql
mysql -u root -p < db/mysql/objects.sql
mysql -u root -p < db/mysql/seed.sql

psql cloudledger_vectors -f db/vector/schema.sql
cd db/vector && pip install -r requirements.txt && python embed_and_seed.py && cd ../..

# 3. Run the app
npm install
npm run dev
```

Open `http://localhost:3000`. Do this *before* you're in front of anyone —
first load can take a few seconds while Next.js compiles.

## 3. What's on each screen

| Page | Who can see it | What it shows |
|---|---|---|
| `/` | Anyone (logged out) | Marketing/landing page — redirects signed-in users straight to their dashboard |
| `/login` | Anyone | Sign-in form, collapsible demo-account picker |
| `/admin/dashboard` | Admin only | Stat tiles (clients, running instances, current-month total), a revenue-by-month chart, an instance-status breakdown chart, a searchable client table |
| `/client/instances` | Everyone (scoped) | Searchable instance table, start/stop/terminate actions (terminate asks for confirmation), status badges |
| `/client/billing` | Everyone (scoped) | Searchable invoice table with Paid/Pending/Overdue badges |
| `/support` | Everyone (scoped) | Submit a ticket; semantic search over past tickets by meaning, not keywords |

Role-based access is enforced **twice**: `proxy.ts` redirects anyone who
tries to reach `/admin/*` without the Admin role, and every API route
independently re-derives the caller's client scope from their session JWT —
so even a crafted request can't see another client's data.

## 4. Suggested script (~6 minutes)

**1. Land on the homepage, then sign in as Admin** (`admin@cloudledger.dev`)
   - Point out the dashboard's three stat tiles, the revenue chart, and the
     instance-status pie chart — all computed live from MySQL, not hardcoded.
   - Scroll to the client table — 8 clients, one (Umbrella Analytics) shown
     as Suspended.

**2. Sign out, sign in as `bilal@cloudledger.dev` (DevOps, Initech only)**
   - Go to **Instances**. Note the table only shows Initech's instances —
     same login form, completely different data, because access is scoped
     server-side by role.
   - Click **Terminate** on a running instance → a confirmation dialog
     appears before anything happens → confirm → a toast confirms the
     status change and the table refreshes.

**3. Show the safety trigger**
   - Still as an account with instance access, try to imagine provisioning
     an instance for Umbrella Analytics (Suspended). The database itself
     rejects it via `trg_prevent_deploy_suspended_client` — this is a
     MySQL-level guarantee, not just a UI restriction. (Easiest to show
     this one directly in a MySQL client if you want to show the raw
     `SIGNAL SQLSTATE '45000'` error — see `README.md` → Testing notes.)

**4. Sign in as `carmen@cloudledger.dev` (Billing, Globex only)**
   - Go to **Billing**. Show the invoice table spans three months with a
     realistic mix of Paid/Pending/Overdue — generated by the
     `sp_generate_monthly_invoice` stored procedure from real usage-log
     data, not typed in by hand.

**5. Go to Support**
   - Submit a new ticket.
   - Then run a semantic search using *different wording* than any actual
     ticket — e.g. search **"my server keeps charging me even though I
     turned it off"** — and show it correctly surfaces tickets titled
     "Server still billing after shutdown" and "Instance won't stop
     accruing cost" even though none of those words match exactly. This is
     cosine similarity over `all-MiniLM-L6-v2` embeddings in pgvector, not
     keyword search.

**6. Close on the polish**
   - Toggle dark mode from the sidebar.
   - Resize the window (or open dev tools' device toolbar) to show the
     sidebar collapsing into a mobile sheet menu.
   - Visit a bogus URL to show the branded 404 page.

## 5. Talking points if asked "why is this well-built"

- **Two-layer authorization** — UI redirect *and* independent per-request
  server checks, so the API can't be tricked by hiding a nav link.
- **Real relational integrity** — foreign keys, `CHECK` constraints,
  triggers, a view, and a transactional stored procedure, not just app-side
  validation.
- **A second, purpose-fit database** — PostgreSQL + pgvector alongside
  MySQL, because free-text ticket search is a fundamentally different
  query shape than billing data, and using the right tool for each avoids
  forcing keyword search onto a semantic problem.
- **Consistent, accessible UI system** — shadcn/ui + Radix-based primitives
  throughout (not one-off styled divs), full light/dark theming, and
  loading/empty/error states everywhere instead of blank screens or raw
  stack traces.

## 6. If something looks empty or broken right before you present

- **Dashboard/tables look empty:** the MySQL/Postgres containers probably
  aren't running — `docker compose up -d`, wait a few seconds, then
  `npm run dev` again.
- **Semantic search returns nothing:** the ticket embeddings weren't
  seeded — rerun `python db/vector/embed_and_seed.py` from `db/vector/`
  (needs `PGVECTOR_URL` set, see `README.md`).
- **Want a clean slate:** rerun all three MySQL files in order
  (`schema.sql`, `objects.sql`, `seed.sql`) — `schema.sql` drops and
  recreates every table, so this is safe to redo anytime before a demo.
